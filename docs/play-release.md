# Releasing to Google Play

What has to be true before an upload is accepted, and how to make each one true.
Written after an audit found five things that would each have failed a
submission on their own.

The build is local (`gradlew`), not EAS cloud: this project builds its own
binaries so a release is reproducible on the machine holding the signing key,
with no queue and no third party in the path. `eas.json` still carries a
`production` profile if that ever changes.

## The signing key

`android/` is generated by `expo prebuild` and is not tracked, so signing config
cannot live in `build.gradle`. It is applied by
[`plugins/withReleaseSigning.js`](../apps/mobile/plugins/withReleaseSigning.js)
on every prebuild.

Make an upload key once, **outside the repository**:

```sh
keytool -genkeypair -v \
  -keystore ~/keys/waves-upload.jks \
  -alias upload -keyalg RSA -keysize 2048 -validity 10000
```

Then put the four properties in `~/.gradle/gradle.properties` — never in the
repo, never in `.env`:

```properties
WAVES_UPLOAD_STORE_FILE=C:/Users/you/keys/waves-upload.jks
WAVES_UPLOAD_STORE_PASSWORD=…
WAVES_UPLOAD_KEY_ALIAS=upload
WAVES_UPLOAD_KEY_PASSWORD=…
```

Back the `.jks` up somewhere that is not this machine. **Enrol in Play App
Signing** when the app is created; then Google holds the key that actually signs
what users install, and a lost upload key can be reset by support. Without it, a
lost key ends the app — no future version can ever be shipped under that
listing.

With no properties set the release build falls back to debug signing and says so
in the log. That keeps `assembleRelease` working for sideloading; `bundleRelease`
refuses outright, because an AAB exists only to be uploaded and Play rejects a
debug-signed one.

## The version

`expo.android.versionCode` in `app.json`. Play orders uploads by it, refuses a
duplicate, and refuses to go backwards — permanently, for the life of the
listing. Bump it for **every** upload, including one that only fixes the store
description's typo.

`expo.version` (`1.0.0`) is the name people see. It also drives
`runtimeVersion: { policy: 'appVersion' }`, which decides which OTA updates a
binary will accept: **changing `version` orphans every installed build from new
OTA updates** until they take the new binary from the store. Change it when the
native side changed; leave it alone for a JS-only release.

## Building the bundle

```sh
cd apps/mobile
npx expo prebuild --clean          # regenerates android/ with every plugin applied
cd android
./gradlew bundleRelease            # → app/build/outputs/bundle/release/app-release.aab
```

`--clean` matters more than it looks. The plugins that matter here — release
signing, the App Links intent filter, Sentry's native config — are all applied at
prebuild, and an `android/` directory generated before a plugin was added simply
does not have it. That is the whole of the "Sentry native configuration is
missing" warning.

An AAB cannot be installed on a phone. To test the exact artefact Play will
serve, use [bundletool](https://github.com/google/bundletool) to build APKs from
it, or upload to the internal test track and install from there.

## What the console needs

### Account deletion

Play requires **two** paths for any app with accounts: one inside the app, and a
public URL that works for somebody who has already uninstalled it.

- In-app: Settings → Delete my data (`app/settings/delete-account.tsx`).
- Web: `https://wavs.co.in/en/delete-account`
  ([`website/src/app/[locale]/delete-account`](../website/src/app/%5Blocale%5D/delete-account/page.tsx)).

That page, the in-app screen, and the retention section of the privacy policy
say the same thing three times, and they have to agree. Change one, change all
three.

### Privacy policy

`https://wavs.co.in/en/privacy`. Must match the Data safety form below; a
mismatch is a takedown, not a warning.

### Data safety

Declared per data type, and this app collects a lot of them: financial
information (the ledger), name and email, contacts, location, photos, audio,
device identifiers. For each: whether it is collected, whether it is shared,
whether it is encrypted in transit, and whether it can be deleted.

The honest answers are already written down — the privacy policy's "What we
collect", "Where it is stored" and "Who processes it for us" sections were
written to be the source for this form.

### Listing assets

None of these are in the repo:

- 512×512 icon (32-bit PNG, no alpha)
- 1024×500 feature graphic
- at least 2 phone screenshots, 16:9 or 9:16, min 320px
- short description (80 chars) and full description (4000)

### Content rating and target audience

The questionnaire is short. "Not directed at children" matches the privacy
policy's Children section.

## Before the first upload

- [ ] Upload key made, backed up, four properties set
- [ ] Play App Signing enrolled
- [ ] `versionCode` bumped
- [ ] `bundleRelease` produces a signed AAB
- [ ] `SENTRY_ORG` and `SENTRY_PROJECT` set, so the native SDK is in the binary
      and source maps upload — `EXPO_PUBLIC_SENTRY_DSN` alone gives JS-only
      reporting with unreadable native stack traces
- [ ] Deletion URL and privacy URL both returning 200
- [ ] Data safety form matches the privacy policy
- [ ] `/.well-known/assetlinks.json` deployed and returning the app's
      fingerprints, so invite links open the app (it must be live _before_ the
      build is installed — Android checks at install time)

## Known gaps

- **`SYSTEM_ALERT_WINDOW`** is in the manifest and nothing in this repo appears
  to ask for it. Play flags draw-over-other-apps. Worth tracing to whichever
  dependency requests it and removing if it is unused.
- **iOS has no `associatedDomains`**, so the same invite links open Safari there.
