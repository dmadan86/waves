# Signing in with a phone number

The code that lands on somebody's phone is generated by GoTrue and delivered by
[`otp-send`](../supabase/functions/otp-send/handler.ts), an edge function
standing in Supabase's Send SMS Hook. This is what has to be true for it to work,
in the order it has to become true, and how to tell which piece is missing when
it does not.

Everything in the app and in the function is built and deployed. What is left is
an account with Twilio, a registration, a handful of secrets and one switch —
none of which live in this repository.

## Why the hook exists at all

GoTrue can talk to Twilio by itself; `[auth.sms.twilio]` in
[`config.toml`](../supabase/config.toml) is that setting, and it stays off. Two
things come from owning the delivery step instead:

1. **A cap that can actually be enforced.** The app calls GoTrue directly, so a
   per-day limit written into the app is advice a modified client ignores. In the
   hook it is the server, keyed on the number, and there is no other door. Four
   codes to a number a day, from `LIMITS['otp-send']`.
2. **The rail is a setting, not a rewrite.** `OTP_CHANNEL` picks SMS or WhatsApp.
   Nothing else in the system knows the difference — the app calls the same
   `signInWithOtp` and verifies the same `type: 'sms'` either way.

It is also why Twilio _Verify_ is off. Verify mints and checks its own code;
inside a send hook that would put two different codes in play and neither one
would validate.

```
app  ──signInWithOtp──▶  GoTrue  ──signed POST──▶  otp-send  ──▶  Twilio  ──▶  phone
                           │                          │
                    generates the code          counts it, then sends it
```

## What is already done

Verified against the Mumbai project (`ywojpnfyxxltvihqmcni`) on 2026-09-12:

- `otp-send` is deployed and `ACTIVE`, with `verify_jwt = false` — the caller is
  GoTrue, which carries no user session. What it carries instead is a
  standardwebhooks signature, checked before anything else is read.
- Both rails are implemented and tested.
- The client side is finished: `sendOtp`/`verifyOtp` in
  [`apps/mobile/src/lib/auth.tsx`](../apps/mobile/src/lib/auth.tsx), the screen at
  [`apps/mobile/src/app/phone.tsx`](../apps/mobile/src/app/phone.tsx).

## What is not

- No Twilio secrets are set on the project, and no hook secret.
- `[auth.hook.send_sms] enabled = false`.
- `[auth.sms] enable_signup = false`, and it stays that way (ADR-006): a number
  signs somebody back in or attaches to an account a guest already has. It never
  opens a new one.

# SMS

## 1. DLT registration — start here, it is the long pole

A2P SMS to an Indian number is gated on DLT registration with the operators
through TRAI. **Unregistered traffic is dropped by the carrier**, after Twilio
has accepted the request and billed for it, which means it fails somewhere
neither the logs nor Twilio's console will tell you about.

Three registrations, in order, on any operator's DLT portal (Jio, Airtel, VI —
one registration propagates to all of them):

1. **Principal Entity.** Your business, with GST or incorporation documents. You
   get a PE ID.
2. **Header** — the six-character sender ID the message comes from, e.g.
   `WAVESA`. Transactional/service headers are the category for an OTP.
3. **Content template.** The exact text, with `{#var#}` where the code goes.
   This is matched **character for character** at delivery time. A full stop you
   add later is a message the carrier drops.

Reckon on one to two weeks. Then register the same PE ID, header and template
IDs with Twilio (Console → Messaging → Regulatory Compliance / India DLT) and
attach them to the Messaging Service you will send from.

Outside India none of this applies and step 1 is: buy a number.

## 2. Twilio

- A number, or an alphanumeric sender ID for India.
- A **Messaging Service** (Console → Messaging → Services) holding it. For India
  this is what carries the DLT registration, which is why the handler prefers
  `TWILIO_MESSAGING_SERVICE_SID` over a bare `From`.
- Console → Account → API keys & tokens → create a **standard API key**. The
  handler prefers `TWILIO_API_KEY_SID`/`TWILIO_API_KEY_SECRET` over the account
  auth token: a key is scoped, revokable on its own, and losing it does not mean
  rotating the token every other integration shares. The account SID is still
  required either way — a key says who is calling, never which account is billed.

## 3. Secrets

```sh
npx supabase secrets set --project-ref ywojpnfyxxltvihqmcni \
  SEND_SMS_HOOK_SECRET=v1,whsec_...           \
  OTP_CHANNEL=sms                             \
  TWILIO_ACCOUNT_SID=AC...                    \
  TWILIO_API_KEY_SID=SK...                    \
  TWILIO_API_KEY_SECRET=...                   \
  TWILIO_MESSAGING_SERVICE_SID=MG...          \
  TWILIO_SMS_BODY='{code} is your Waves verification code.'
```

`TWILIO_SMS_BODY` must be the DLT-registered text with `{code}` where `{#var#}`
is. It is a secret only because that is where edge configuration lives; there is
nothing confidential in it. Leave it unset outside India and the default is used.

Without a Messaging Service, set `TWILIO_SMS_FROM` to the number instead.

# WhatsApp

The other rail, and the default when `OTP_CHANNEL` is unset. It sidesteps DLT
entirely — WhatsApp business messaging is not A2P SMS — at the cost of a
different queue: a Meta Business Manager account, a phone number with no WhatsApp
account on it, and **Meta business verification**, which is also measured in
weeks and caps you at 250 unique recipients per 24h until it clears.

1. Twilio Console → Messaging → Senders → WhatsApp senders → sign up a sender.
2. Content Template Builder → type **Authentication**
   (`twilio/authentication`), copy-code button, language `en`. A business-initiated
   message must be a template Meta approved; free text is only allowed inside a
   24-hour window a sign-in has no reason to be in. The body is Meta's own text,
   so there is little to reject and approval is usually minutes.
3. Secrets: `TWILIO_WHATSAPP_FROM=whatsapp:+...` and `TWILIO_OTP_CONTENT_SID=HX...`
   in place of the SMS pair, and no `OTP_CHANNEL`.

The template's language is fixed at approval time, so a person using Waves in
Tamil still gets an English authentication message. One Content SID per locale
and a map in the handler would fix it — worth doing later, not worth blocking on.

The Twilio Sandbox (Messaging → Try it out) proves the plumbing in ten minutes,
but every tester has to join it by texting a code and it will not carry an
authentication template. It is not a staging environment.

## The hook secret, which is set twice

One value, two runtimes, configured by different mechanisms — and both are
needed. Generate it in the Supabase dashboard (Authentication → Hooks → Send SMS
hook) and copy the whole `v1,whsec_...` string.

The edge function, which **verifies** the signature, takes it as
`SEND_SMS_HOOK_SECRET` through `supabase secrets set`, alongside everything
above.

GoTrue, which **creates** it, reads `supabase/.env` (gitignored):

```sh
SEND_SMS_HOOK_SECRETS=v1,whsec_...
```

Note the plural. `config.toml` reads `env(SEND_SMS_HOOK_SECRETS)`, and
`supabase secrets set` does not reach GoTrue — a hook configured that way is
signed by nobody and refused by us. Same value in both, or every genuine request
is answered 401 while the function looks deployed and the hook looks enabled.

## The switch

In `config.toml`, `[auth.hook.send_sms] enabled = true`. Then:

```sh
npx supabase config push --project-ref ywojpnfyxxltvihqmcni
```

**Read the whole file before pushing.** Anything it does not say, the CLI supplies
a default for and pushes anyway, silently overwriting whatever the dashboard had.
The first push on this project turned off anonymous sign-ins, manual identity
linking and email confirmation in one go — and anonymous sign-ins is the guest
flow, which is the app.

Flip it in the same change that sets the secrets, never before. Enabled without
them, every send fails and somebody sits on the code screen waiting for a message
that was never posted.

## Proving it

A dev build stubs the send and accepts `000000`, because there is usually no
Twilio account behind it and a walkable app matters more than a real message. To
exercise the real path, set `EXPO_PUBLIC_DEV_REAL_OTP=true` in
`apps/mobile/.env.local` and restart Metro. The guard stays anchored on `__DEV__`,
so the flag cannot resurrect the magic code in a release build.

Use a number that **already has an account**. Signup is off, so a new number is
refused by design, and that refusal is not a bug in the send path.

```sh
npx supabase functions logs otp-send --project-ref ywojpnfyxxltvihqmcni
```

| What you see                                    | What it means                                                                                                                                          |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `401 That signature does not match`             | The two copies of the hook secret differ.                                                                                                              |
| `500 SEND_SMS_HOOK_SECRET is not set`           | The edge-function secret is missing entirely.                                                                                                          |
| `500 Code sending is not configured`            | The rail has no sender: no Messaging Service and no `From`, or WhatsApp without a Content SID.                                                         |
| `502` + `twilio send failed`                    | Twilio refused it. The reason is in the log line beside it — never returned to the caller, because it can name the sender and the account.             |
| `429`                                           | Four codes to that number today.                                                                                                                       |
| Nothing at all                                  | GoTrue never called us: the hook is still disabled, or pointed at the wrong URL.                                                                       |
| A `201` from Twilio and no message on the phone | On an Indian number, DLT. The text did not match the registered template, or the header is not attached to the service. Twilio cannot see this either. |

That last row is the one that costs an afternoon. Twilio accepting a message
means Twilio accepted it, not that a carrier delivered it; check the message's
status in the Twilio console, where a DLT rejection shows as `undelivered` with
error 30008 or an India-specific code.

## The cap

Four codes to a number a day, counted **before** the message is sent. A provider
outage therefore still burns an attempt; the alternative — send first, count
after — lets a script spend the whole day's allowance before the first count
lands.

If the limiter itself errors it fails open, the same trade the shared limiter
makes everywhere: the only way that happens is the database being unreachable,
and refusing every sign-in during a database blip does more damage than the abuse
it guards against.

## If you want a different provider

The provider is about twenty-five lines of `handler.ts` and a different set of
secrets. The hook contract, the signature check, the cap and the whole app are
untouched by it.

For SMS in India: MSG91, Gupshup, Kaleyra, Karix, Plivo, Textlocal. They bill in
INR, and most will walk the DLT registration with you — worth real money, since
that is the step measured in weeks. None of them can skip it.

For WhatsApp: Meta's Cloud API direct (no reseller margin, but you look after a
System User token), 360dialog (Cloud API at a flat fee), or an Indian BSP.

## Turning it off

Set `[auth.hook.send_sms] enabled = false` and push the config. GoTrue goes back
to having no SMS provider, phone sign-in stops working, and every other door —
email, Google, Apple, guest — is untouched. The secrets can stay; a disabled hook
never reads them.
